# B3. 주괴 K개씩 합치기 — 해설 (GOLD, 보스)

## 1. 출제 의도

이 세트가 목표로 하는 최종 지점은 "K가 고정값이 아니라 입력으로 주어졌을 때도, 패딩 공식과 그리디 논리를 일반적인 형태로 세울 수 있는가"다. B2에서 K=3이라는 구체적인 사례로 통찰을 익혔다면, B1은 그 통찰을 문자 그대로 일반화하기만 하면 되도록 설계했다 — 코드 구조는 거의 동일하고, 상수 `3`이 변수 `K`로 바뀔 뿐이다. 다만 K가 N과 무관하게 주어지도록 제약을 잡아서(`K>N`인 경우까지 포함), "패딩이 아주 많이 필요한 극단적인 경우"까지 스스로 다뤄봐야 진짜로 일반 공식을 이해했다고 볼 수 있게 만들었다.

## 2. 문제를 보고의 사고 흐름

1. B2를 풀어봤다면 "어차피 K=3이 K로 바뀌는 거 아닌가?"라는 가설을 세우게 된다. 실제로 맞는 가설이지만, 검증해야 할 게 하나 있다 — K가 3보다 훨씬 크거나, 심지어 N보다 클 수도 있다는 점이다.
2. 패딩 공식 `(N-1) mod (K-1)`을 일반 K로 확장해서 다시 유도해보면: 매번 K개를 합쳐 개수가 K-1개씩 줄어드니, 최종적으로 1개가 남으려면 (시작 개수 - 1)이 (K-1)의 배수여야 한다. 나머지가 `r`이면 부족한 개수는 `(K-1) - r`이다.
3. 그런데 `K > N`인 경우를 생각해보면(예: 주괴 3개, K=5), 진짜 주괴 개수만으로는 애초에 한 번도 K개를 채울 수 없다. 이때도 공식이 그대로 통하는지 확인해야 한다 — 공식대로면 부족한 개수가 `K-1`개 이하로 계산되는데, 이 값을 그대로 더미로 채우면 "가짜로 채운 개수 + 진짜 개수 = K"가 되어 단 한 번의 합치기로 끝나는 상황이 만들어진다. 즉 공식이 K와 N의 대소관계와 무관하게 항상 성립한다는 걸 확인하는 게 이 문제의 핵심 검증 포인트다.
4. 그다음은 지금까지와 동일한 그리디다: 패딩까지 마친 전체 집합에서 가장 작은 K개를 반복해서 합친다.

## 3. 풀이

`r = (N-1) mod (K-1)`을 계산해서, `r != 0`이면 무게 0인 더미를 `(K-1) - r`개 추가한다. 이후 최소 힙에서 K개씩 꺼내 합치고 비용을 누적하는 과정을 원소가 1개 남을 때까지 반복한다. N=1이면 K값과 무관하게 항상 0을 출력한다(공식을 그대로 적용해도 `r=0, pad=0`이 나와 반복문이 아예 돌지 않으므로 별도 분기가 사실 필요 없지만, 명확성을 위해 앞에서 먼저 처리했다).

이 문제에서 짚어야 할 성능 이슈가 하나 있다. K가 크면 한 번에 K개씩 poll하는 비용이 걱정될 수 있는데, 실제로는 전체 poll 횟수를 계산해보면 항상 `2·N_padded` 이하로 묶인다는 걸 알 수 있다. 매 병합이 K개를 소모하고 개수를 K-1개 줄이므로, 총 병합 횟수는 `(N_padded-1)/(K-1)`이고, 총 poll 횟수는 `K × 그 값 = N_padded × K/(K-1)`이다. K≥2이면 `K/(K-1) ≤ 2`이므로, K가 아무리 커도 총 poll 횟수는 항상 `N_padded`의 2배를 넘지 않는다. 즉 K값과 무관하게 항상 O(N log(N+K))에 끝난다는 걸 미리 확인해두었기 때문에, 시간 제한을 K의 크기와 상관없이 여유 있게 잡을 수 있었다.

## 4. 코드 해설 (Java)

```java
if (N <= 1) { System.out.println(0); return; }
long r = (long) (N - 1) % (K - 1);
int pad = (r == 0) ? 0 : (int) (K - 1 - r);

PriorityQueue<Long> pq = new PriorityQueue<>();
for (long x : w) pq.add(x);
for (int i = 0; i < pad; i++) pq.add(0L);

long cost = 0;
while (pq.size() > 1) {
    long s = 0;
    for (int t = 0; t < K; t++) s += pq.poll();
    cost += s;
    pq.add(s);
}
System.out.println(cost);
```

- B2 코드와 나란히 비교하면 차이가 명확하다: `int K = 3;`이라는 상수 선언이 사라지고 입력에서 읽은 변수 `K`로 대체됐을 뿐, 패딩 계산식과 힙 로직의 형태는 동일하다. 이건 우연이 아니라 "일반화가 코드 구조를 바꾸지 않아야 한다"는 걸 보여주려고 의도한 설계다.
- 세 개를 한 줄에 이어 poll하던 B2와 달리 여기서는 `for (int t = 0; t < K; t++) s += pq.poll();`로 K번 반복하는 형태를 썼다. K가 고정값이 아니라 가변이기 때문에 반복문으로 일반화한 것이 자연스러운 선택이다.
- `pad`를 계산할 때 `(long)(N-1) % (K-1)`처럼 캐스팅을 신경 쓴 이유: N, K가 각각 int 변수지만 `N-1`이 int 연산으로 먼저 계산된 뒤에 long으로 캐스팅되면 이미 int 오버플로가 나 있을 수 있다는 걱정을 원천 차단하기 위해서다. 이 문제의 N은 최대 20만이라 실제로는 `N-1`이 int로도 전혀 문제없지만, "값이 커질 수 있는 자리는 항상 먼저 long으로 승격시키고 계산한다"는 습관을 코드에 반영해뒀다.
- `pad`가 최대 `K-1`(최대 약 20만) 수준으로 항상 작다는 걸 미리 알고 있었기 때문에, 더미를 담을 별도의 큰 배열을 만들지 않고 그냥 힙에 하나씩 `add(0L)`로 넣는 단순한 반복으로 처리했다. 만약 패딩이 N 규모를 훨씬 초과할 수 있었다면 이 방식은 위험했겠지만, 공식상 `pad < K ≤ 200,000`이 항상 보장되므로 안전하다.

## 5. 검증기(다른 접근)로 다시 보기

검증기는 B2의 two-queue 기법을 일반 K로 확장했다(매번 `get_min()`을 K번 호출해서 합치고, 남은 개수를 K-1씩 줄인다). 이 문제는 K가 매우 크거나(`K=200000`) 매우 작은 N에 큰 K가 붙는(`N=10, K=200000`) 극단적인 조합까지 다뤄야 해서, 패딩 공식이 그 경계에서도 무너지지 않는지가 가장 걱정되는 지점이었다. 그래서 실제 제작 과정에서는 두 구현(힙 vs two-queue)을 N=1~20, K=2~50 범위에서 수천 건 랜덤 비교하는 것 외에도, `K=N`, `K=N+1`, `K=N+2`처럼 패딩이 딱 0개/1개/여러 개 필요한 경계를 일부러 짚어 명시적으로 검사했다. 두 구현이 완전히 다른 자료구조(힙 vs 정렬된 큐 두 개)로 짜여 있었기 때문에, 만약 패딩 공식 자체나 반복 종료 조건에 경계값 실수가 있었다면 두 결과가 갈라져서 바로 드러났을 것이다.
