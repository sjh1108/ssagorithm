# A3. 두 상자의 카드 합의 K번째 수 — 해설 (GOLD, 보스)

## 1. 출제 의도

이 세트의 최종 목표는 "이분 탐색 + 투 포인터 카운팅"이라는 조합을 배열이 두 개인 상황까지 확장할 수 있는지 확인하는 것이었다. A3에서 카운팅 기법을, A2에서 그 기법을 이분 탐색의 판정 함수로 얹는 법을 각각 익혔다면, A1은 그 두 아이디어를 그대로 가져가되 "배열이 하나가 아니라 둘"이라는 조건 하나만 바꿔서 난이도를 끌어올린다. 딱 하나만 바뀌었지만 이게 생각보다 큰 차이를 만드는데, 두 배열을 오가며 투 포인터를 굴리려면 "어느 쪽을 오름차순으로 순회하고 어느 쪽을 단조 감소 포인터로 둘 것인가"를 스스로 설계해야 하고, 그 포인터가 이분 탐색의 매 반복(각 `mid` 값)마다 리셋되어야 한다는 점도 놓치기 쉬운 부분이다.

N, M을 각각 최대 10만으로 잡은 이유는 두 상자의 가능한 조합 수 N×M이 최대 10^10이 되게 하기 위해서다. 이 정도면 모든 조합을 나열하는 건 메모리에 올리는 것조차 불가능하므로, "조합을 나열하지 않고 개수만 세는" 접근이 강제된다. K 역시 최대 10^10이라 int로는 담을 수조차 없다는 걸 지문에 명시했는데, 이건 "K를 int로 선언했다가 파싱 단계에서부터 값이 깨지는" 실수를 의도적으로 유도한 것이다.

## 2. 문제를 보고의 사고 흐름

1. A2를 풀어봤다면 가장 먼저 드는 생각은 "A2랑 거의 똑같은데 배열이 두 개네?"일 것이다. 실제로 큰 틀(정렬 + 이분 탐색 + 카운팅)은 동일하다.
2. 다만 카운팅 함수를 다시 설계해야 한다. "상자 A와 상자 B에서 각각 하나씩 뽑은 합이 S 이하인 조합이 몇 개인가?"를 물어야 하는데, 두 배열을 정렬해두면 A2와 비슷한 관찰이 성립한다: A를 오름차순으로 하나씩 보면서, "이 A[i]와 짝지어 합이 S 이하가 되는 B의 원소는 어디까지인가"를 구하면 된다.
3. 여기서 중요한 관찰: A[i]가 커질수록(오름차순으로 진행할수록), 짝지어질 수 있는 B의 최댓값은 절대 커지지 않고 같거나 작아진다(단조성). 그래서 B 쪽 포인터 j를 M-1(가장 큰 값)에서 시작해 A[i]가 커질 때마다 필요하면 줄여나가기만 하면 되고, 다시 늘릴 필요가 없다 — 즉 j는 전체 순회 동안 최대 M번만 움직인다.
4. i는 N번, j는 M번만 움직이므로 카운팅 함수 한 번 호출에 O(N+M)이 걸린다. 이걸 이분 탐색(약 32회 반복) 안에서 호출하면 O((N+M) log(range))가 되어 충분히 빠르다.
5. 여기서 반드시 주의할 점: j 포인터는 "카운팅 함수 한 번을 실행하는 동안에만" 단조 감소한다. 이분 탐색이 다음 `mid`로 넘어가 카운팅 함수를 다시 호출할 때는 j를 M-1로 되돌려야 한다. 이걸 놓치고 j를 전역으로 유지하면 이전 호출에서 줄어든 상태 그대로 다음 호출을 시작하게 되어 답이 틀린다.

## 3. 풀이

두 배열 A, B를 각각 오름차순 정렬한다. 답의 범위를 `[A[0]+B[0], A[N-1]+B[M-1]]`로 잡고 이분 탐색을 한다. 후보 `mid`에 대해:

```
j = M-1
cnt = 0
for i in 0..N-1:
    while j >= 0 and A[i]+B[j] > mid: j -= 1
    if j < 0: break
    cnt += (j+1)     // B[0..j]가 전부 유효
```

`count_le(mid) >= K`를 만족하는 가장 작은 `mid`가 답이다. A2와 마찬가지로 이 값이 "실제로 존재하는 합"과 정확히 일치한다는 논리도 동일하게 성립한다. 전체 시간복잡도는 정렬 O((N+M)log N)와 이분 탐색 O((N+M)log(range))를 합쳐 O((N+M)log N)에 근접한다.

## 4. 코드 해설 (Java)

```java
private static long countLE(long[] a, long[] b, int n, int m, long s) {
    long cnt = 0;
    int j = m - 1;
    for (int i = 0; i < n; i++) {
        while (j >= 0 && a[i] + b[j] > s) j--;
        if (j < 0) break;
        cnt += (j + 1);
    }
    return cnt;
}
```

- `j = m - 1`을 함수 맨 앞, 즉 매 호출마다 새로 선언한 이유가 앞서 말한 "이분 탐색 반복마다 리셋되어야 한다"는 요구사항 때문이다. 만약 이걸 함수 밖의 전역/클래스 변수로 빼서 호출 간에 공유했다면, 두 번째 이분 탐색 반복부터 잘못된 상태에서 시작해 답이 틀린다. 이 문제에서 가장 흔하게 나오는 구현 버그가 바로 이 지점이다.
- `if (j < 0) break;`를 넣은 이유: A[i]가 매우 커서 B의 어떤 원소와 짝지어도 `s`를 넘는 상황이 오면, 그 이후의 i는 A가 정렬되어 있으니 더 커질 뿐이라 절대 조건을 만족할 수 없다. 이때 굳이 남은 i를 계속 순회할 필요가 없어 바로 끊었다(정확성에는 영향 없지만, 불필요한 반복을 줄이는 최적화다. break를 안 해도 `j<0`인 상태에서 `j+1=0`이 더해지므로 결과 자체는 같다).
- `lo = A[0]+B[0], hi = A[N-1]+B[M-1]`로 탐색 범위를 잡은 이유: 두 배열 모두 정렬되어 있으니 가능한 가장 작은 합과 가장 큰 합이 정확히 이 값들이다. A2처럼 여유를 더 둘 필요 없이 정확한 하한/상한을 바로 알 수 있는 게 두 배열 문제의 특징이다.
- `N, M`은 int로 받아도 되지만(각각 최대 10만) `K`는 반드시 long이어야 한다(최대 10^10). 그리고 배열 인덱싱에 int가 필요하니 `N`, `M`은 int로 캐스팅해서 쓰고, `K`와 합 계산, 카운트 누적에는 전부 long을 썼다 — 이렇게 "인덱스는 int, 값과 개수는 long"으로 역할을 나눠서 선언하는 습관이 이런 대규모 카운팅 문제에서 실수를 줄여준다.

## 5. 검증기(다른 접근)로 다시 보기

검증기는 투 포인터 대신, A의 각 원소마다 `bisect_right(B, mid - A[i])`로 B에서 조건을 만족하는 개수를 이분 탐색으로 구해서 더하는 방식을 썼다(O(N log M) per 호출). 두 배열을 다루는 이 문제에서 특히 이 교차검증이 중요한 이유는, 앞서 말한 "j 포인터 리셋 실수"처럼 상태를 잘못 공유하는 버그가 투 포인터 구현에만 나타나는 유형의 실수이기 때문이다. 완전히 다른 방식(원소별 독립적인 이분 탐색이라 이전 호출의 상태를 전혀 기억하지 않음)으로 같은 값을 얻었을 때만 "이 카운팅이 맞다"고 믿을 수 있다. 실제로 이 문제를 만들 때도 두 구현과 별개로 작은 N, M에 대한 완전탐색(O(N×M log(N×M)))을 추가로 돌려 세 번째 교차검증을 했다.
