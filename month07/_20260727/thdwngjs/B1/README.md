# B1. 주괴 두 개씩 합치기 — 해설 (SILVER)

## 1. 출제 의도

세트 B의 보스 문제(B1)는 "임의의 K개씩 묶어 합칠 때 최소 비용"인데, 그 문제의 핵심 통찰인 "더미(무게 0) 주괴로 개수를 맞춘다"는 아이디어는 K=2일 때는 아예 필요가 없다(두 개씩 합치는 건 항상 끝까지 진행할 수 있으므로). 그래서 B3는 일부러 그 통찰이 필요 없는 가장 단순한 사례로 만들었다 — "매번 가장 작은 두 개를 합치는 게 항상 최적"이라는, 그리디 자체의 순수한 형태만 연습시키기 위해서다. 여기서 최소 힙(우선순위 큐)을 다루는 기본기를 확실히 잡아두면, B2에서 "패딩"이라는 개념 하나만 추가로 얹는 데 부담이 없어진다.

무게 상한을 10,000으로, N 상한을 200,000으로 잡은 이유는 총 비용이 확실하게 32비트를 넘도록 만들기 위해서다. 실제로 최댓값 근처 케이스를 모범답안으로 돌려보면 총 비용이 350억대까지 나오는데(2^31-1은 약 21억), 이 정도로 여유 있게 넘겨야 "합을 int에 누적하다가 오버플로로 틀리는" 실수를 확실히 잡아낼 수 있다.

## 2. 문제를 보고의 사고 흐름

1. "두 개씩 합치는 데 드는 비용은 두 무게의 합, 이걸 최소화" — 이 문장을 보고 가장 먼저 확인해야 할 건 "합치는 순서가 총 비용에 영향을 주는가"이다. 예시로 무게 1,2,3,4를 손으로 몇 가지 순서로 합쳐보면(1+2를 먼저 하는 경우와 1+4를 먼저 하는 경우) 총 비용이 달라진다는 걸 알 수 있다 — 즉 순서가 중요한 최적화 문제다.
2. 왜 "가장 작은 두 개를 먼저 합치는 게 유리한가"를 생각해보면: 작은 값일수록 이후 합쳐질 때마다 그 값이 여러 번 누적된다(트리 구조로 보면 뿌리에서 먼 잎일수록, 즉 나중에 합쳐질수록 최종 비용에 곱해지는 "깊이"가 얕다). 그래서 가장 작은 값들을 먼저 합쳐서 깊은 곳(자주 재사용되지 않는 위치)에 묻어두는 게 유리하다는 직관을 얻을 수 있다. 이건 정확히 허프만 코딩에서 "빈도가 낮은 문자를 트리의 깊은 곳에 배치한다"는 논리와 같다.
3. 이 직관을 그대로 구현하려면 "현재 남아있는 것 중 가장 작은 두 개"를 반복해서 빠르게 꺼내야 하는데, 이런 연산(최솟값 꺼내기 + 새 값 넣기)을 반복하는 데 가장 적합한 자료구조가 최소 힙(우선순위 큐)이다.

## 3. 풀이

모든 주괴 무게를 최소 힙에 넣는다. 힙에 원소가 2개 이상 남아있는 동안: 가장 작은 두 값을 꺼내 합치고, 그 비용을 답에 더한 뒤, 합쳐진 새 무게를 다시 힙에 넣는다. 힙 연산이 총 N-1번(매번 2개를 꺼내고 1개를 넣으니 원소 수가 1개씩 줄어듦) 일어나고 각 연산이 O(log N)이므로 전체 O(N log N)이다.

N=1이면 이미 주괴가 하나뿐이라 합칠 필요가 없으므로 0을 출력해야 한다 — 이 경우를 놓치면 힙이 비어있는 상태에서 poll()을 두 번 호출하려다 예외가 나거나, 반복문 조건을 잘못 잡아 문제가 생긴다.

## 4. 코드 해설 (Java)

```java
if (N <= 1) { System.out.println(0); return; }
PriorityQueue<Long> pq = new PriorityQueue<>();
for (long x : w) pq.add(x);
long cost = 0;
while (pq.size() > 1) {
    long a = pq.poll();
    long b = pq.poll();
    long s = a + b;
    cost += s;
    pq.add(s);
}
System.out.println(cost);
```

- `N <= 1`을 맨 앞에서 처리한 이유는 위에서 말한 대로다. 이런 "자명한 경계"를 반복문 진입 전에 먼저 걸러두면, 반복문 내부 로직을 "항상 2개 이상 남아있다"고 가정하고 단순하게 짤 수 있어 코드가 깔끔해진다.
- `PriorityQueue<Long>`을 쓴 이유는 Java 기본 `PriorityQueue`가 최소 힙이라 별도의 비교자(Comparator) 없이 자연스러운 오름차순 정렬로 동작하기 때문이다. 만약 최대 힙이 필요했다면 `Collections.reverseOrder()`를 넣어야 하지만, 여기서는 항상 가장 작은 값을 꺼내야 하므로 기본 동작 그대로 쓰면 된다.
- `PriorityQueue<Long>`처럼 박싱된 `Long`을 쓰면 원시 타입 `long[]` 기반 직접 구현 힙보다 약간 느리지만(오토박싱 오버헤드), N이 20만 수준에서는 체감상 문제되지 않는다(실측 0.2초 내외). 만약 N이 훨씬 크거나 시간 제한이 빡빡했다면 원시 타입 배열로 직접 min-heap을 구현하는 편이 더 안전하다.
- `long s = a + b; cost += s;`처럼 합산 결과를 항상 `long`으로 유지한 이유는 앞서 말한 32비트 오버플로 때문이다. 무게 자체는 최대 1만이라 개별 값은 작지만, 합쳐지는 과정이 반복되면서 값이 기하급수적으로 누적되어 최종 비용은 수백억 단위까지 커질 수 있다.

## 5. 검증기(다른 접근)로 다시 보기

검증기는 힙을 아예 쓰지 않고 "two-queue 기법"으로 같은 답을 구한다. 원본 무게를 정렬해서 큐 하나(`q1`)에 넣고, 병합으로 새로 생기는 값들이 쌓이는 큐 하나(`q2`, 처음엔 비어 있음)를 별도로 둔다. 두 큐의 맨 앞을 비교해서 더 작은 쪽을 꺼내는 `get_min()`을 두 번 호출해 합치고, 그 결과를 `q2` 뒤에 붙이는 과정을 반복한다.

이 방식이 성립하는 이유는 "q2에 쌓이는 값들이 항상 비내림차순으로 생성된다"는 성질 때문이다(매 단계 그 시점에 존재하는 전역 최솟값 두 개만 소모하므로, 새로 생기는 합도 이전에 생긴 합보다 작을 수 없다). 힙을 전혀 쓰지 않는 완전히 다른 구현이라, 힙 기반 모범답안에서 "가장 작은 두 개를 정말로 제대로 꺼내고 있는지" 같은 로직 실수를 잡아내는 데 효과적이다.
