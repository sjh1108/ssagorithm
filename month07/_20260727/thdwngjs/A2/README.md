# A2. 카드 합의 K번째 수 — 해설 (GOLD)

## 1. 출제 의도

A3에서 "합이 X 이하인 쌍의 개수를 O(N)에 세는 법"을 익혔다면, 이제 그 함수를 "도구"로 취급해서 한 단계 위의 질문에 답하게 만들고 싶었다. "K번째로 작은 합이 무엇인가"라는 질문은 언뜻 정렬처럼 보이지만, 가능한 합의 개수가 최대 C(200000,2)≈2×10^10개라 전부 만들어서 정렬하는 건 애초에 불가능하다. 이 지점에서 "값을 직접 찾는 대신, 값을 하나 잡고 그보다 작거나 같은 게 몇 개인지 세어서 위치를 좁혀나가자"는 이분 탐색의 발상이 자연스럽게 필요해지도록 제약을 짰다. A2는 A1(두 배열 버전)로 가기 전에 "이분 탐색 값 + A3의 카운팅 함수"라는 조합 자체를 단일 배열이라는 더 단순한 무대에서 먼저 연습시키는 역할을 한다.

카드 값을 양수(1 이상 15억 이하)로만 제한한 것은 A3와 다른 선택인데, 이유가 있다. A2/A1의 출력은 "쌍의 개수"가 아니라 "실제 합 값"이라서, 그 값 자체가 32비트를 넘게 만들려면 개별 카드 값을 크게 잡아야 한다(두 값의 합이 32비트를 넘으려면 각 값이 대략 10억 이상이어야 함). 그래서 상한을 15억으로 올려 두 값의 합이 최대 30억까지 나오게 만들었다.

## 2. 문제를 보고의 사고 흐름

1. "만들 수 있는 모든 합을 정렬했을 때 K번째" — 직관적으로는 "모든 쌍의 합을 구해서 정렬한 뒤 K번째를 꺼낸다"가 떠오르지만, 쌍의 개수가 N(N-1)/2 ≈ 2×10^10개라 배열에 담는 것 자체가 불가능하다.
2. 그렇다면 값을 직접 나열하지 않고 답을 찾을 방법이 필요하다. 여기서 "답이 S 이하인 합이 몇 개인가?"라는 질문을 던져보면, 이건 정확히 A3에서 이미 풀어본 문제와 같은 형태다(X 자리에 S를 넣으면 된다).
3. 그리고 "S 이하인 합의 개수"라는 함수는 S가 커질수록 절대 줄어들지 않는 단조함수다. 단조성이 있으면 이분 탐색을 쓸 수 있다 — "count_le(S) ≥ K를 만족하는 가장 작은 S"를 찾으면 되고, 그 S가 정확히 K번째로 작은 합이 된다는 걸 알 수 있다(계단함수가 오직 실제로 존재하는 합 값에서만 값이 뛰기 때문에, "처음으로 K 이상이 되는 지점"은 반드시 실제 달성 가능한 합 값과 정확히 일치한다).
4. 즉 "A3의 카운팅 함수를 판정 함수로 삼아 이분 탐색을 돌리면 된다"는 결론에 도달한다.

## 3. 풀이

배열을 정렬한 뒤, 답이 존재할 수 있는 범위를 `[2·min, 2·max]`로 잡고 이분 탐색을 한다. 후보 값 `mid`에 대해 A3와 동일한 `count_le(mid)`(투 포인터, O(N))를 호출해서 `count_le(mid) >= K`이면 답 후보를 `mid` 이하로 좁히고, 아니면 `mid`보다 크게 좁힌다. 탐색 범위의 폭이 약 30억이라 이분 탐색은 대략 32번 반복되고, 매 반복이 O(N)이니 전체는 O(N log N + N log(range))다.

이분 탐색으로 "K번째 값을 직접" 찾을 수 있는 이유를 다시 한번 짚으면: `count_le`는 계단 함수이고, 계단이 올라가는 지점은 오직 실제로 존재하는 합의 값들뿐이다. 그러므로 `count_le(S-1) < K <= count_le(S)`를 만족하는 S는 다중집합에서 K번째로 작은 원소값과 정확히 같다. 이건 "K번째 원소를 찾는 이분 탐색"의 표준적인 논리이고, 동점(같은 합이 여러 쌍에서 나오는 경우)도 자동으로 올바르게 처리된다.

## 4. 코드 해설 (Java)

```java
Arrays.sort(a);
long lo = 2 * a[0], hi = 2 * a[N - 1];
while (lo < hi) {
    long mid = lo + (hi - lo) / 2;
    if (countLE(a, N, mid) >= K) hi = mid;
    else lo = mid + 1;
}
System.out.println(lo);
```

- `countLE`는 A3의 투 포인터 함수를 그대로 가져왔다(다만 문제 X 자리에 이분 탐색 후보값 `mid`가 들어간다는 점만 다르다). 문제를 설계할 때부터 "A2의 판정 함수 = A3의 정답 함수"가 되도록 의도했기 때문에, 실제로 A3를 풀어본 학생이라면 이 함수를 거의 그대로 재사용할 수 있어야 한다.
- `mid = lo + (hi-lo)/2`로 쓴 이유: `(lo+hi)/2`로 써도 이 문제의 값 범위(최대 30억 정도)에서는 long 오버플로가 나지 않지만, 습관적으로 오버플로에 안전한 형태로 작성했다. 일반적으로 이분 탐색 중앙값 계산에서 `lo+hi`가 자료형의 최댓값을 넘는 실수가 잦기 때문에, 값의 크기와 무관하게 항상 이 형태를 쓰는 습관을 들이길 권한다.
- `K`를 `long`으로 읽어야 한다는 점이 이 문제의 또 다른 함정이다. N=200,000이면 K의 최댓값이 N(N-1)/2 ≈ 2×10^10로 int 범위를 넘는다. 입력을 파싱하는 순간부터 long이 아니면 그 자리에서 값이 깨진다.
- 이분 탐색 범위를 `[2·min, 2·max]`로 잡은 이유: 두 카드는 서로 달라야 하지만 값 자체는 같을 수 있으므로(같은 수가 적힌 카드가 두 장 있을 수 있음), 최소 합은 배열에서 가장 작은 두 값의 합이 아니라 "가장 작은 값 두 개를 합친 것"과 같은 하한을 여유 있게 잡기 위해 `2·min`을, 최대 합은 `2·max`를 상한으로 잡아 확실히 답을 포함하는 구간에서 시작했다.

## 5. 검증기(다른 접근)로 다시 보기

검증기는 같은 이분 탐색 뼈대를 쓰되, `count_le`만 A3의 검증기와 같은 방식(원소별 `bisect_right` 누적 후 자기 자신 보정)으로 바꿔치기했다. 이렇게 하면 "이분 탐색 골격은 같지만 카운팅 로직은 독립적으로 구현된" 두 코드가 나오는데, 이 설계에는 한계가 있다는 것도 알아둘 필요가 있다 — 만약 이분 탐색 자체의 논리(예: 탐색 범위 설정, 종료 조건)에 개념적인 결함이 있었다면 두 구현이 똑같이 틀려서 교차검증을 통과해버릴 수 있다. 그래서 실제 제작 과정에서는 이 위험을 없애기 위해 완전탐색 방식의 세 번째 브루트포스 코드까지 추가로 만들어 소규모 입력에서 세 구현을 서로 비교했다(수천 건 스트레스 테스트 통과). 검증기 하나만으로 "절대 안전하다"고 안심하지 말고, 알고리즘의 큰 틀 자체는 별도로 손검증하거나 브루트포스와 대조하는 습관이 중요하다.
