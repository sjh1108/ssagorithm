# B2. 주괴 세 개씩 합치기 — 해설 (GOLD)

## 1. 출제 의도

B3에서 "가장 작은 것부터 합치는 그리디"를 익혔다면, B2는 거기에 이 세트의 진짜 핵심 통찰 — "개수가 K개씩 딱 맞아떨어지지 않으면 무게 0인 가짜 주괴로 채운다" — 를 처음 도입하는 자리다. K를 3으로 고정한 이유는, 이 통�찰을 "가장 작고 구체적인 사례"로 보여주고 싶었기 때문이다. K=3이면 더미가 필요한지 아닌지가 "N이 홀수냐 짝수냐"라는 아주 단순한 조건으로 결정되고((N-1) mod 2), 필요한 더미도 최대 1개뿐이라 손으로도 검증하기 쉽다. 이 단순한 사례에서 통찰을 확실히 이해하고 나면, B1에서 K가 임의의 값으로 일반화됐을 때도 같은 논리를 그대로 확장하면 된다는 걸 자연스럽게 받아들일 수 있다.

## 2. 문제를 보고의 사고 흐름

1. "정확히 세 개씩 묶어야 한다"는 조건을 보고 가장 먼저 드는 의문은 "주괴가 항상 3의 배수 개수만큼 남을까?"이다. 예시로 주괴가 4개 있는 경우를 생각해보면: 3개를 합치면 2개가 남는데(1개는 새로 합쳐진 것, 1개는 원래 있던 것), 2개로는 "정확히 세 개"라는 조건을 만족할 수 없어 막힌다.
2. 이 상황을 해결하려면 개수를 3개씩 묶어서 정확히 1개로 줄어들 수 있는 형태로 미리 맞춰둬야 한다. 매번 3개를 합치면 개수가 2개(=K-1개)씩 줄어드니, 최종적으로 1개가 남으려면 시작 개수가 "1 + 2의 배수" 형태여야 한다. 즉 (N-1)이 2로 나누어떨어져야 한다.
3. 만약 그렇지 않다면(즉 N이 짝수라면), 비용에 전혀 영향을 주지 않는 무게 0인 "가짜 주괴"를 1개 추가해서 개수를 맞추면 된다는 아이디어에 도달한다. 무게가 0이므로 아무리 이르게 합쳐 넣어도(오히려 일찍 합칠수록 유리하다 — B3의 논리와 같음) 실제 비용에는 손해가 없다.
4. 그다음은 B3와 동일하다: (패딩까지 포함한) 전체 주괴 중 가장 작은 3개를 반복해서 합치면 된다.

## 3. 풀이

`r = (N-1) mod 2`를 계산해서, `r != 0`이면 무게 0인 더미를 `1`개 추가한다(K=3이므로 `K-1=2`, 나머지는 항상 0 또는 1뿐이라 더미는 최대 1개만 필요하다). 패딩까지 마친 뒤에는 최소 힙에서 3개씩 꺼내 합치고, 그 비용을 누적하고, 합쳐진 값을 다시 넣는 과정을 남은 게 1개가 될 때까지 반복한다. N=1이면 애초에 합칠 필요가 없으므로 0을 출력한다.

## 4. 코드 해설 (Java)

```java
if (N <= 1) { System.out.println(0); return; }
int K = 3;
long r = (N - 1) % (K - 1);
int pad = (r == 0) ? 0 : (int) (K - 1 - r);

PriorityQueue<Long> pq = new PriorityQueue<>();
for (long x : w) pq.add(x);
for (int i = 0; i < pad; i++) pq.add(0L);

long cost = 0;
while (pq.size() > 1) {
    long s = pq.poll() + pq.poll() + pq.poll();
    cost += s;
    pq.add(s);
}
System.out.println(cost);
```

- `K`를 상수 3으로 박아둔 이유는 이 문제 자체가 "K=3 고정"이기 때문이다. B1에서는 이 자리가 입력으로 바뀌는데, 코드 구조를 거의 그대로 유지한 채 `K`만 변수로 바꾸면 B1의 풀이가 된다는 걸 미리 보여주기 위해 일부러 이런 형태로 짰다(실제로 B1의 코드와 나란히 놓고 비교하면 차이가 딱 그 한 줄뿐이라는 걸 알 수 있다).
- `pad = (K - 1 - r)`이라는 공식이 왜 맞는지: 남은 나머지가 `r`이면, `K-1`개 단위로 채워야 할 다음 배수까지 부족한 개수가 정확히 `K-1-r`이다. `r==0`이면 이미 딱 맞으므로 별도 처리 없이 0을 더미로 넣는다(사실 `pad=0`인 경우 반복문이 그냥 안 도는 것과 같다).
- 더미를 실제로 `pq.add(0L)`로 힙에 넣은 이유는, "가짜 주괴"라는 개념을 코드에서 특별 취급하지 않고 그냥 "무게 0인 진짜 원소"로 취급해서 나머지 로직(3개씩 꺼내 합치기)을 완전히 동일하게 재사용하기 위해서다. 특별한 분기 없이 자연스럽게 로직에 녹아들도록 만드는 게 구현 실수를 줄이는 핵심이었다.
- `pq.poll() + pq.poll() + pq.poll()`처럼 세 번의 poll을 한 줄에 이어 쓴 이유는 단순히 코드를 간결하게 유지하기 위해서다. Java는 이런 식으로 연속된 부작용(poll이 매번 힙에서 원소를 제거하는 부작용)이 있는 호출을 좌에서 우로 순서대로 평가하도록 보장하므로, 항상 가장 작은 세 값을 정확히 한 번씩 꺼낸다.

## 5. 검증기(다른 접근)로 다시 보기

검증기는 B3와 같은 two-queue 기법을 K=3에 맞게 확장했다(매번 `get_min()`을 세 번 호출해서 합치고, 남은 개수를 K-1=2씩 줄인다). 실제로 제작 과정에서 이 부분에서 진짜 버그가 하나 나왔다 — 처음에는 "정렬한 뒤 더미 0들을 배열 끝에 이어붙이는" 순서로 짰는데, 그러면 큐의 앞쪽에 있어야 할 더미(무게 0이니 당연히 가장 먼저 쓰여야 함)가 정렬 후 맨 뒤로 밀려나 오름차순 불변식이 깨지는 문제였다. "더미를 먼저 이어붙이고 그다음에 전체를 정렬한다"로 순서를 바꿔서 해결했다. 이 사례는 "패딩값을 언제, 어떤 순서로 자료구조에 반영하는가"가 겉보기엔 사소해 보여도 정답에 직접 영향을 준다는 걸 보여준다.
