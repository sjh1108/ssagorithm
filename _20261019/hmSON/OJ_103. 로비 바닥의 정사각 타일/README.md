# OJ_103. 로비 바닥의 정사각 타일

크기별 재고와 비용이 정해진 정사각 타일로 모든 `#`칸을 겹치지 않게 덮을 때 드는 최소 비용을 구해야 함

격자 크기가 최대 `10 x 10`이고 타일 종류도 (`1 x 1` ~ `5 x 5`) 5가지 뿐이므로 규모 자체는 크지 않음<br>
그러나 "어느 칸에 어떤 크기를 놓는가"의 조합이 서로 영향을 주고, 큰 타일이 항상 비용 관점에서 유리한 것도 아니므로 그리디로 해결할 수 없음

따라서 **모든 배치 조합을 시도하되, 탐색이 폭발하지 않도록 가지치기하는 백트래킹**이 요구됨


## 1. 탐색 기준 고정 - 가장 왼쪽 위의 빈 칸
> **매 단계에서 아직 덮이지 않은 칸 중 가장 왼쪽 위 칸 하나를 고정하고, 그 칸을 왼쪽 위 모서리로 삼는 타일 설치 시도**

이 칸은 반드시 어떤 타일로든 덮여야 하고, 그 타일의 왼쪽 위 모서리가 될 수밖에 없다는 점을 이용<br>
덮을 위치는 좌측 상단부터 시작하는 순차 탐색으로 확인하여 "어느 칸을 먼저 덮어야 하는가"의 기준을 정함

**이 칸을 덮지 않는 경우는 존재할 수 없으므로, 모든 타일의 설치 시도가 끝나면 즉시 return**


## 2. 상태 관리
> `map[i][j]` = `true`면 이미 덮였거나 덮을 수 없는 칸, `false`면 덮어야 할 칸

문제에서 주어지는 격자의 상태는 오직 `#`, `.` 두 가지로만 주어지므로 별도의 방문 배열 없이 `map[][]` 배열 자체를 **덮을 수 있는 칸과 없는 칸**으로 분류하여 관리<br>
타일을 놓을 때 해당 영역을 전부 `true`로 반전시키고, 이후 같은 영역을 다시 `false`로 반전시키면 원상복구 할 수 있음


## 3. 가지치기
타일을 설치할 수 없는 경우는 총 3가지가 있고, 상황에 따라 다른 선택을 해야 함

### 3-1. 바닥 크기에 의한 타일 크기 상한
```java
n = Math.min(5, Math.min(h, w));
```

로비 격자보다 큰 타일은 애초에 놓을 수 없으므로 탐색 범위에서 제외하고 입력값을 받을 필요조차 없음

### 3-2. 재고 확인
해당 크기 타일의 재고가 `0`이라면 시도 자체를 건너뛰어야 하므로 `continue`

### 3-3. 크기 증가에 따른 조기 중단
```java
if(!checkSquare(i, j, k)) break;
```

작은 크기의 타일(`1 x 1`)부터 시작하여 오름차순으로 타일 설치 가능 여부를 확인함<br>
따라서 `k x k` 크기의 타일의 재고가 있는데 놓을 수 없는 환경이라면 `(k+1) x (k+1)` 크기 이상의 타일도 놓을 수 없음

좌측 상단 모서리가 고정된 상태에서 크기가 늘어나면 큰 정사각형이 작은 정사각형을 완전히 포함하므로, `continue`가 아닌 **`break`로 남은 크기 타일의 시도 자체를 전부 잘라내고 복귀**


## 4. 복잡도
- 각 단계에서 시도하는 분기 : 최대 5가지 (타일 크기)
- 탐색 깊이 : 최악의 경우 `#` 칸 수만큼, 즉 최대 100

이론상 상한은 크지만 실제로는 재고 제한(크기별 최대 5장)과 배치 가능 여부 검사가 대부분의 가지를 잘라냄<br>
또한 왼쪽 위 칸 고정으로 중복 경로가 제거되어, `10 × 10` 규모에서는 5초 제한 안에 충분히 들어옴

공간 복잡도는 격자 배열과 재귀 스택으로 $O(HW)$
