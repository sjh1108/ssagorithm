# A3. 카드 합 세기 — 해설 (SILVER)

## 1. 출제 의도

세트 A는 A1(보스)이 "두 배열의 곱집합에서 K번째로 작은 합 찾기"인데, 이걸 처음부터 가르치면 학생은 이분 탐색과 투 포인터 카운팅을 동시에 소화해야 한다. 그래서 두 아이디어를 분리해서 각각 따로 연습시키기로 했고, A3는 그중 "카운팅" 쪽만 떼어낸 문제다. 이분 탐색은 아예 등장하지 않고, "정렬된 배열에서 합 조건을 만족하는 쌍을 O(N)에 세는 법"만 익히면 풀린다.

N을 200,000까지 잡은 이유는 명확하다. O(N²) 완전탐색이면 최대 2×10^10번 연산이라 시간 제한 안에 절대 못 끝난다는 걸 참가자가 직접 느끼게 하기 위해서다. 그리고 답(쌍의 개수) 자체가 최대 C(200000,2) ≈ 2×10^10으로 32비트 정수를 가볍게 넘어버리는데, 이건 "정렬+투 포인터까지는 맞게 짰는데 int로 답을 받아서 틀리는" 흔한 실수를 유도하려는 의도적 설계다. 카드 값 범위에 음수를 포함시킨 것도 같은 맥락이다 — 두 포인터 기법이 "정렬만 되어 있으면 부호와 무관하게 동작한다"는 걸 스스로 확인하지 않은 채 "양수만 되는 기법"으로 오해하는 경우가 있어서, 음수만 있는 케이스와 양음 혼합 케이스를 반드시 넣었다.

## 2. 문제를 보고의 사고 흐름

1. "서로 다른 두 카드의 합이 X 이하인 조합의 개수" — 일단 가장 단순하게 생각하면 모든 쌍 (i,j)를 다 검사(이중 for문)하면 된다. 하지만 N=200,000이면 이 방법은 시간 제한 안에 못 끝난다는 걸 제약에서 바로 알 수 있어야 한다.
2. 그럼 "합이 X 이하"라는 조건을 빠르게 판정하려면 뭔가 순서 정보가 있어야 한다 → 정렬해보자는 생각으로 이어진다.
3. 정렬된 배열에서 가장 작은 값 A[i]와 가장 큰 값 A[j]의 합을 본다. 만약 A[i]+A[j] ≤ X라면, A[j]보다 작거나 같은 모든 값(즉 A[i+1], ..., A[j])과 A[i]를 더해도 합은 A[i]+A[j] 이하이므로 전부 조건을 만족한다. 즉 i 하나를 고정했을 때 "j부터 그보다 왼쪽인 i+1까지"의 (j-i)개 쌍을 한 번에 확정할 수 있다.
4. 반대로 A[i]+A[j] > X라면, A[j]는 어떤 상대와 짝지어도(심지어 가장 작은 A[i]와도) 조건을 만족하지 못하는 값이므로, A[j]는 이제 완전히 제외하고 j를 하나 줄여야 한다.
5. 이 두 규칙을 번갈아 적용하면 i는 오른쪽으로, j는 왼쪽으로만 움직이고 서로 만나면 끝난다 — 즉 각 포인터가 총 N번 이하로만 움직이므로 O(N)에 모든 쌍을 다 센 것과 같은 효과를 낸다.

## 3. 풀이

배열을 오름차순 정렬한다. 투 포인터 `i=0, j=N-1`, 누적 개수 `cnt=0`으로 시작해서:

- `A[i]+A[j] <= X`이면 `cnt += (j-i)` 하고 `i += 1`
- 아니면 `j -= 1`

`i < j`인 동안 반복한다. 정렬에 O(N log N), 투 포인터에 O(N)이 걸려 전체 O(N log N)이다.

## 4. 코드 해설 (Java)

```java
Arrays.sort(a);
int i = 0, j = N - 1;
long cnt = 0;
while (i < j) {
    if (a[i] + a[j] <= x) {
        cnt += (j - i);
        i++;
    } else {
        j--;
    }
}
System.out.println(cnt);
```

- `cnt`와 `x`를 처음부터 `long`으로 선언한 이유는 위에서 말한 대로 답이 32비트를 넘기 때문이다. 입력을 받는 시점부터 long으로 파싱하지 않으면 X 자체가 -2×10^9~2×10^9 범위라 int로도 아슬아슬하게 들어가긴 하지만, 두 값을 더하는 `a[i]+a[j]` 계산과 답 누적에서 반드시 long이 필요하다.
- `while(i<j)`로 종료 조건을 잡은 이유: i==j가 되면 같은 카드를 자기 자신과 짝짓는 셈이 되어 "서로 다른 두 장"이라는 조건을 어기게 된다. 그래서 반드시 엄격한 부등호를 써야 한다.
- 입력을 빠르게 읽기 위해 `DataInputStream` 기반의 바이트 단위 파서를 썼다. N이 최대 20만이라 `Scanner`나 `BufferedReader.readLine().split()` 조합도 이론상 통과는 하지만, 시간 제한을 넉넉히 확보하고 싶어서(그리고 여러 개의 대용량 스트레스 케이스를 연속으로 도는 채점 환경을 고려해서) 더 빠른 방식을 기본으로 채택했다.

## 5. 검증기(다른 접근)로 다시 보기

모범답안이 투 포인터라면, 검증기는 완전히 다른 경로로 같은 답을 구하게 만들어야 구현 버그를 잡을 수 있다. 여기서는 "각 원소 A[i]마다, A[i]와 짝지어 합이 X 이하가 되는 원소가 몇 개인지"를 이분 탐색(`bisect_right(A, X - A[i])`)으로 세는 방식을 썼다.

이 값을 모든 i에 대해 더하면 `(i,k)` 순서쌍 전체(자기 자신과 짝짓는 경우, 그리고 (i,k)와 (k,i)를 둘 다 세는 경우)를 다 포함한 값이 나온다. 그래서 자기 자신과 짝지어지는 경우의 수(`2*A[i] <= X`인 i의 개수)를 빼고 2로 나누면 우리가 원하는 "서로 다른 카드 두 장, 순서 없음" 개수가 된다. 투 포인터와 계산 경로 자체가 다르기 때문에, 만약 둘 중 하나에서 경계값(`<=`를 `<`로 잘못 쓰는 등) 실수가 있었다면 두 출력이 어긋나서 곧바로 드러난다.
